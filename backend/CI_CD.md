# Backend CI/CD

## CI and deployment flow

`backend-ci.yml` runs on relevant pull requests to `main`, pushes to `feat/backend-setup`, and manual dispatch. It checks Ruff, unit and API tests, PostgreSQL 16 integration tests, and a Docker build. The PostgreSQL runner uses disposable local databases and separate application and migration roles. The image artifact expires after seven days; an approval delayed longer requires a fresh run. The deployment workflow invokes the same CI against its selected commit. Backend CD uses its own concurrency group with `cancel-in-progress: false`.

`backend-azure.yml` runs on relevant pushes to `main`, or manual dispatch from `main`. A deploy must target the current `origin/main` SHA. After CI and Environment approval, it pushes the CI image with a full SHA tag, compares the digest returned by Docker push with ACR metadata, and configures the existing App Service with `registry/repository@sha256:...`. The tag is a lookup aid, never the deployment authority. An existing SHA tag causes failure, even if someone moved that tag; the workflow will not overwrite it. The workflow does not create or recreate the App Service, plan, or ACR. It does not change App Settings, registry credentials, or network configuration.

Immediately before updating the App Service image, every deploy, including manual `action=deploy`, fetches `origin/main` and requires an exact SHA match. A queued older run exits without changing the image. A conscious `action=rollback` skips this freshness check and skips CI, because it restores a previously successful release. It still requires Environment approval.

After both HTTP checks return 200 **with the expected `X-Release-Id`**, the workflow uploads `backend-release-<attempt>` containing the deployed digest, source SHA, image reference, and release ID. A rollback takes `release_run_id`, checks GitHub's run metadata (`main`, this workflow, successful conclusion), downloads that run's release artifact, verifies its fields and that the digest exists in ACR, and deploys that exact digest. A SHA tag merely existing in ACR is never accepted as proof of a release. GitHub Actions artifacts are retained for 90 days; arrange a separately governed durable release ledger if rollback must remain available longer. Protect Actions artifact access and the workflow file through repository permissions and branch protection. The release record is a workflow provenance record, not cryptographic image attestation.

The current configured image is recorded in the run summary. If it is a legacy tag, it is not eligible for trusted rollback. **The first deployment through this workflow cannot roll back to an earlier legacy image through this workflow.** Preserve a manually verified recovery procedure before the first CD. Do not delete ACR manifests that still have active release records. A digest prevents a moved tag from silently changing what App Service requests; verify App Service digest references on a staging instance before production use.

## GitHub setup and OIDC

Configure these Actions variables: `BACKEND_ACR_NAME`, `BACKEND_RESOURCE_GROUP`, `BACKEND_WEBAPP_NAME`, `BACKEND_BASE_URL` (HTTPS origin), `BACKEND_AZURE_CLIENT_ID`, `BACKEND_AZURE_TENANT_ID`, and `BACKEND_AZURE_SUBSCRIPTION_ID`. No database connection string, JWT key, ACR password, or production secret belongs in the workflows. The deploy job alone has `id-token: write`; it also needs `actions: read` to inspect and download release records.

Create a GitHub Environment named **`backend-production`** with required reviewers, prevent self-review where available, and restrict deployments to the protected `main` branch. The reviewer must verify the release SHA, migration state, database compatibility, and target digest before approval. The Environment is an operational gate for every deploy and rollback. In GitHub branch protection, require passing backend CI, PR review, and protection of `.github/workflows/backend-azure.yml` and Terraform changes (for example CODEOWNERS). The path-filtered CI workflow may be skipped; do not require its check unconditionally unless a separate always-running required check is added. Prevent direct pushes and force pushes to `main`; restrict who may dispatch deployment workflows. These settings must be configured in GitHub; this repository change cannot set them.

The default GitHub OIDC subject for a job using this Environment is `repo:OWNER/REPO:environment:backend-production`, **not** `repo:OWNER/REPO:ref:refs/heads/main`. Azure's federated credential matches issuer, audience, and the exact subject, but by itself cannot bind the default subject to one workflow file or the branch. GitHub Environment branch restrictions and branch protection supply those controls. Verify the actual subject for this repository and check whether a custom subject template is in use before setting `backend_github_oidc_main_subject`. If custom subjects are required, design and verify the exact template and adjust Terraform validation first. Do not copy the frontend credential subject. The audience is `api://AzureADTokenExchange` and issuer is `https://token.actions.githubusercontent.com`. The federated credential and GitHub Environment must agree before CD can authenticate.

## Azure access

`terraform/backend-ci.tf` looks up the existing App Service and shared ACR. It creates only the separate backend GitHub identity, its federated credential, and role assignments. The identity needs `Website Contributor` scoped to the backend web app and ACR `Reader` for registry metadata. It needs data-plane push/read permission for the backend image. Inspect ACR's **current** role assignment permissions mode in Azure before choosing `backend_acr_permissions_mode`:

| Current mode | Role | Scope |
| --- | --- | --- |
| RBAC registry permissions | `AcrPush` | Whole shared ACR; Azure RBAC cannot confine this role to one repository. |
| RBAC + ABAC repository permissions | `Container Registry Repository Writer` | ACR role assignment with a reviewed version 2.0 condition for every writer action on `dreamplanner-backend`. Supply the Azure-generated expression as `backend_acr_abac_condition`. |

Do not switch the registry mode as part of this change. Do not apply a Writer role without its reviewed condition in ABAC mode. The simple Terraform check for the repository name is a guard against an empty value, **not** proof that the condition covers every action; review the expression in Azure's condition editor before applying. In RBAC mode the registry-wide `AcrPush` is a real remaining privilege, including potential access to frontend repositories. This change does not modify the frontend identity or its roles. The App Service runtime identity separately needs `AcrPull` in RBAC mode or an appropriate repository reader role in ABAC mode. Check `acrUseManagedIdentityCreds=true`, the selected pull identity, VNet/private DNS for PostgreSQL, Key Vault references, `WEBSITES_PORT=8000`, and runtime settings. Terraform is not applied by CI/CD.

## Production migration gate

The protected `backend-production` Environment pauses the deployment job **before OIDC login, ACR push, or App Service changes**. For every release, the reviewer records whether Alembic migrations are needed. From a separately authorized executor inside the VNet, using only `MIGRATION_DATABASE_URL`, run `alembic current`, review pending SQL and compatibility with both old and new images, confirm backup and recovery, run `alembic upgrade head` once when needed, and verify `alembic current` again. Approve the Environment only after the database is ready for the target image. Do not run production migrations on a GitHub-hosted runner or at container start. For incompatible schema changes, use an expand/contract sequence or a coordinated recovery plan. Image rollback never downgrades schema or data. The gate relies on human review; GitHub cannot infer database compatibility from source changes.

## Smoke test and failure

The Docker build embeds a unique `RELEASE_ID` (`run_id-run_attempt`), returned as `X-Release-Id` on liveness and readiness responses with `Cache-Control: no-store`. CD checks HTTPS `/api/v1/health` and `/api/v1/health/ready` for both 200 and the expected ID. This rejects a 200 from an old instance. It proves only that at least one responding instance serves the requested release and can connect to PostgreSQL; it does not prove every scaled-out instance is updated, that Alembic is compatible, or that business paths work. A failed smoke test fails the workflow, creates no successful release record, and leaves the configured image for diagnosis. It does **not** automatically roll back. An operator inspects logs and database compatibility, then chooses a previously successful `release_run_id` for manual rollback if safe. The first release has no earlier ledger entry.

## Local checks

Before merging, run Ruff lint and format, unit and API tests, PostgreSQL 16 integration tests, Docker build, full `actionlint`, `terraform fmt -check`, and `git diff --check`. Terraform `init -backend=false` and `validate` are useful when provider downloads are available; never run `plan` or `apply` as part of this audit. Local checks cannot verify Azure RBAC mode, federated subject, private network reachability, Environment policy, or actual App Service digest startup.
